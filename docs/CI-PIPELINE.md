# bouncerdata pipeline

_Generated by `ops/scripts/pipeline_guide.py` from `docs/pipeline.json`, using runs up to 25 Nov 2026, 9:32am (Sydney time). Do not edit by hand, except the notes section: rerun the generator._

The three daily GitHub Actions workflows in this repo that feed the cricket models and the site, in the order the data flows: the Cricsheet sync (ball-by-ball results onto the cricsheet release), the Cricinfo scrape (Hawkeye ball data and fixtures onto the cricinfo release, which then starts the predictions run in the bouncer repo), and the blog data build (aggregates the releases into the files the site reads from R2). The predictions run itself lives in the bouncer repo and has its own guide there. The Fox Sports scrape (foxsports-daily.yml) is left out: it starts nothing, and nothing in the predictions run or the blog build reads its release (checked by searching run_predictions_gha.R and build-blog-data.yml for it; whether the local heavy pipeline uses it was not checked). The heavy model-training pipeline (the 15 steps in bouncer's ARCHITECTURE.md) runs by hand on Pete's machine, not in CI, so it is not here.

## Cricsheet daily sync

Workflow: [`cricsheet-daily.yml`](https://github.com/peteowen1/bouncerdata/blob/HEAD/.github/workflows/cricsheet-daily.yml). Median wall time **1 min 44 s** (range 82 s to 51 min 35 s), from the first job starting to the last job ending, over the 5 run(s) listed below.

Checks Cricsheet for matches added in the last 7 days that are not yet on the cricsheet release, and adds them. Most days there is nothing new and the run is a roughly 100 second no-op (reads the manifest, downloads the small recent-matches zip, finds no new match ids, exits): in the last 60 successful runs up to 25 Nov 2026, 56 were no-ops, 3 were incremental syncs where the sync step took 64 to 73 s, and 1 was a manual forced full rebuild where it took 1,524 s. Only scheduled runs are counted here, so the five runs below are the everyday no-op. When there are new matches the sync step also downloads the existing parquet files, merges the new matches in, rebuilds the manifest and uploads; a full rebuild downloads all_json.zip and re-parses every match. The slowest steps in the table are GitHub runner setup (installing R and the bouncer package), which varies a lot from day to day: 2 of the 5 runs below took 26 and 51 minutes only because Setup R or Install R dependencies stalled (21 and 45 minutes in the worst case), not because of any sync work.

**What starts it, and what it starts:** GitHub's own schedule, set for 7:00 UTC (6pm Sydney in summer) but started hours late in recent runs. It can also be run by hand, with a 'force full rebuild' option; manual runs are not counted here. It starts no other workflow: the predictions run and the blog build read its release files (matches.parquet and players.parquet on the cricsheet release) when they next run.

## Cricinfo scrape

Workflow: [`cricinfo-daily.yml`](https://github.com/peteowen1/bouncerdata/blob/HEAD/.github/workflows/cricinfo-daily.yml). Median wall time **17 min 10 s** (range 16 min 30 s to 17 min 32 s), from the first job starting to the last job ending, over the 5 run(s) listed below.

Scrapes ESPN Cricinfo with a browser: ball-by-ball Hawkeye data, match details and scorecards for the newest series, plus a refresh of the status of upcoming fixtures. New files are merged into the combined files on the cricinfo release (one set per format and gender), then the predictions run is started. Only scheduled runs are counted; a manual run with a series list or the force option is a different amount of work.

**What starts it, and what it starts:** GitHub's own schedule, set for 12:00 UTC (11pm Sydney in summer) but started hours late in recent runs. When it finishes, two things start by themselves: it sends a 'cricinfo-complete' dispatch that starts the Predictions Pipeline workflow in the bouncer repo, and its completion also starts the 'Build blog data' workflow in this repo (that run uses the previous predictions, a few minutes before the new ones are ready). A second 'Build blog data' run starts when the predictions finish. Those runs are not stitched into this one.

## How to regenerate

```
python C:/dev/ops/scripts/pipeline_guide.py build --repo-dir <this repo>
```

It reads `docs/pipeline.json` (which workflows and jobs are the pipeline, one line per step) and the latest successful runs through `gh`, saves every response raw, and rewrites this file and `docs/pipeline-summary.json`. It fails if the config names a job, step or log pattern that no longer appears, so a renamed step cannot leave a stale description behind. Steps marked **(not confirmed)** were not checked against the script they run.
